## 1. The Entu visibility mechanic (source-traced)

Aggregation (`utils/aggregate.js`, runs after every mutation) rebuilds each entity's denormalized doc into three buckets:

- `private` — every property (all rows in the `property` collection for the entity; built by `propertiesToEntity`, L337-368, **independent of any prop-def**).
- `domain` — properties whose effective sharing is `domain` or `public`.
- `public` — properties whose effective sharing is `public`.

The read API returns the best bucket the caller's rights allow (owner/editor → private; in-collective/domain caller → domain; anonymous/public → public).

Two independent controls decide what lands where:

**(a) Prop bucketing — capped by the TYPE's own `_sharing` (L112-156).** For each prop-def the code reads the type entity's own `_sharing` (`definitionSharing`, L72/94) and the prop-def's `_sharing` (L86):
- type cap **absent** → every property is private-only.
- type cap `domain` → a `public` prop-def is **downgraded to `domain`** (L118-120); nothing ever reaches the `public` bucket.
- type cap `public` → no downgrade.
- A `public` prop is written to **both** `domain` and `public` buckets (L152-155); a `domain` prop to `domain` only (L148-150).

**(b) The entity's OWN `_sharing` gates PUBLISH (L269-275, exact-match).** After bucketing: the `domain` bucket is kept only if the entity's `_sharing === 'domain'`; the `public` bucket only if `=== 'public'`; otherwise that bucket is deleted.

**Consequence (the load-bearing design fact):** with **one** shared `profile` type, the cap is uniform across the three profile entities, so **the entity's own `_sharing` is the only enforcement point** — exactly as #24 states. For that to work the cap must be permissive (`public`) and the prop-defs must be `public`; the three entities then differ only by their own `_sharing`.

`_sharing` accepts exactly `{public, domain, private}` — `utils/entity.js:198-201`.

## 3. Design

### 3.1 The `profile` type
- New type entity: `name='profile'`, `_type → entity meta-type (…8034)`, `_parent → db-root (…807a)`, `_owner → admin`, and **`_sharing:'public'` set in the create POST**.
  - Cap must be `public`: a `domain` cap would downgrade the public prop-defs to domain, leaving the public profile entity's public bucket empty → deleted at publish (L273) → the public profile would expose nothing publicly.
  - **Create-time trap:** the parent (db-root) is `domain`; entu-api copies a parent's `_sharing` onto a child **only when the payload omits `_sharing`** (`entity.js:296-327`). Omitting it → the type is born `domain` (wrong cap). The explicit `_sharing:'public'` both sets the cap and suppresses the copy.
  - **`_sharing` before any instance (AC):** satisfied — T4.3 creates zero instances (they are lazy, created by members from T4.4). The cap is read fresh at each instance aggregation, so provisioning the type with `_sharing:'public'` from creation makes every future instance bucket correctly.
- Prop-defs (children of the type): each `_type → property meta-type (…8048)`, `_parent → <profileTypeId>`, `name`, `type` (datatype), **`_sharing:'public'`**, plus convention fields (`search:true`, `label` en/et) to mirror the existing person prop-defs. All `public` because the entity's own `_sharing` does the gating; the prop-def must not cap below the entity's level. Rights are inherited: the type gets an explicit `_owner:…8079` and each prop-def inherits owner from the type via `_inheritrights:true`.
- **Prop-def set (NARROW, per Mihkel 2026-08-06):** exactly `name`(string) and `email`(string) — the two fields T4.10 migrates. Everything else (`phone`, `bio`, `photo`, `voice`, …) is **deferred** — additive-cheap to add later (a plain prop-def POST, no re-aggregation of existing values), and `voice`-on-profile-vs-member is undecided.

### 3.2 `person` reduction
- Remove exactly the `name` (`…8068`), `email` (`…8063`), `notes` (`…8069`) prop-defs. **Leave the other ~15 self-supplied prop-defs untouched** (narrow scope, per Mihkel).
- Person entity instances keep their own `_sharing` unchanged (domain/public/private as enumerated); person stays domain-visible.
- **Leave the person type cap = `domain` (unchanged).** A `domain` cap is sufficient for a later domain-visible display-name (a `public` or `domain` prop-def surfaces to the collective on domain-tier persons). Do not raise or lower it.

### 3.3 Additive-safe (the later display-name affordance)
Additive-safety is inherent: a prop-def is a child entity; removing it is a clean `DELETE /entity/{propDefId}` that leaves no tombstone, and a later display-name is a plain POST of a new prop-def child (reuse `name` or a new `display_name` — both work). Keeping the person type cap at `domain` keeps that later domain-visible field readable by other members (the empty-profile fallback source T4.2/T4.8 want). No field is added now.

### 3.4 Residual carried forward — this slice does NOT close domain-readable person PII
The ~15 self-supplied person prop-defs left in place (`idcode`, `birthdate`, `address`, `county`, `town`, `postalcode`, `phone`, `voice`, `bio`, `photo`, `preferences`, `preferred_contact_email`, `language`, `locale`, `timezone`) remain `_sharing:domain` on a `domain`-tier `person`, so **they stay readable by every domain-tier (in-collective) member** on the 2 domain-tier persons (the 128 public-tier persons expose nothing — a domain prop never reaches the public bucket, and a public entity's domain bucket is deleted at publish, `aggregate.js:269`). **T4.3 does not seal this**, and nothing here should be read as if it does. The cheap later close — set those prop-defs `_sharing:private` and re-aggregate the affected persons — is a **separate authorized live mutation recorded on #21**, out of this task's scope.
